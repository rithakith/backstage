# Frontend Plugin Internals

The frontend package is `@local/backstage-plugin-wso2-api-manager`.

## Plugin Registration

Classic frontend plugin registration is in `src/plugin.ts`.

The plugin id is:

```text
wso2-api-manager
```

The plugin provides `Wso2ApiManagerPage` as a routable extension mounted on `rootRouteRef`.

The plugin also declares an optional external route:

```text
viewTechDoc
```

That external route is defined in `src/routes.ts` with params:

```text
namespace, kind, name
```

## Frontend API Refs

The frontend API refs are declared in `src/api/index.ts`.

| API ref id | Purpose |
| --- | --- |
| `plugin.wso2-api-manager.service` | WSO2 API Manager backend client. |
| `plugin.wso2-api-manager.auth` | OAuth API used to get WSO2 access tokens. |

The client implementation is `Wso2ApiManagerClient`.

## Backend Client Discovery

`Wso2ApiManagerClient` resolves the backend base URL with:

```ts
discoveryApi.getBaseUrl('wso2-api-manager')
```

This depends on the backend plugin being registered with the same plugin id.

## Request Behavior

The client helper:

- Sends `Accept: application/json` for JSON routes.
- Sends `Content-Type: application/json` for `POST` and `PUT`.
- Adds `X-WSO2-Access-Token` when a WSO2 token is passed.
- Throws an error when the backend response is not OK.
- Parses successful JSON responses.
- Throws a parse error if a route expected JSON but returned non-JSON text.

Streaming-style methods do not use the JSON helper:

- `getServiceDefinition`
- `getApiWsdl`

Those methods call `fetchApi.fetch` directly and return text or `Blob`.

## Main Page Behavior

`Wso2ApiManagerPage` uses the WSO2 API client and OAuth API to load operational data. The inspected source shows calls to:

- `getHealth`
- `refreshCatalog`
- `getGateways`
- `getServices`
- `getServiceUsage`
- `getServiceDefinition`

Review note: the frontend calls `getHealth('/health')`, but the inspected backend router does not currently define `GET /health`.

The main page also reads catalog entities and uses annotations to classify:

- Regular APIs.
- API products.
- MCP servers.
- Services.
- APIs discovered from gateways.

The source optimizes catalog reads by selecting only metadata and annotations where possible.

## Entity Card Behavior

The entity cards depend on annotations generated by the catalog backend module.

Important examples:

| Component | Key annotations |
| --- | --- |
| `EntityWso2ApiOverviewCard` | `wso2.com/api-id`, `wso2.com/api-documents`, `wso2.com/api-endpoints`, `wso2.com/api-discovery-type` |
| `EntityWso2ApiDefinitionCard` | `wso2.com/api-id`, `wso2-gateway.com/api-id`, endpoint annotations, API type annotations |
| `EntityWso2ApiDocumentsCard` | `wso2.com/api-id`, `wso2.com/api-documents` |
| `EntityWso2McpToolsCard` | `wso2.com/mcp-tools` |
| `EntityWso2ApiProductResourcesCard` | `wso2.com/product-resources` |
| `EntityWso2AboutCard` | WSO2 API metadata, owner, lifecycle, context, version, and endpoint annotations |

## Entity Predicates

`src/utils.ts` contains two simple predicates:

| Predicate | Condition |
| --- | --- |
| `isWso2Api(entity)` | `metadata.annotations['wso2.com/api-id']` is present. |
| `isMcpEntity(entity)` | `metadata.annotations['wso2.com/is-mcp-server'] === 'true'`. |

## Developer Notes

- Treat the catalog annotations as the contract between the catalog module and the frontend cards.
- When adding new frontend features, first decide whether the data should come from entity annotations, the backend runtime API, or both.
- Use annotations for data that is stable enough to be catalog state.
- Use backend routes for runtime data, privileged WSO2 operations, downloads, streaming, and operations requiring tokens.
